# TODO: несколько Telegram-аккаунтов в одном сервере

Статус: спроектировано (2026-11-12), план проверен по коду и исправлен (2026-11-12),
реализация не начата.

Цель: из одного чата (Claude, Codex, ChatGPT Work) работать с двумя и более аккаунтами
Telegram и явно выбирать, с каким. **Все аккаунты подключаются лениво** — при первом
обращении к ним, сколько бы аккаунтов ни было, хоть один. Если аккаунт отпал (сессия
отозвана, дубликат, нет связи), сервер не падает и остальные аккаунты работают: на
обращение к отпавшему приходит понятное сообщение с командой перелогина именно этого
аккаунта. Пользователь с одним аккаунтом видит всё как раньше.

Семь фаз, каждая — отдельная ветка, отдельный PR и **отдельный свежий чат на Sonnet**.
Порядок по умолчанию строгий: 01 → 02 → … → 07. Допустимая параллель: фаза 05
(установщики) опирается только на 01 и может идти одновременно с 02–04, но по умолчанию —
по очереди.

Перед началом любой фазы прочитать `CLAUDE.md` (инварианты, релиз), разделы этого файла
до «Фаза 01» и свою фазу целиком; из предыдущих фаз — только их «Итог реализации».

## Принятые решения (не переобсуждать)

1. **Метка аккаунта** — то, что пользователь называет в чате («рабочий» → `work`).
   Хранится как суффикс ключа в `config.env`: `TELEGRAM_SESSION_STRING_<МЕТКА>`.
   Канонический вид — как у апстрима (`telegram_mcp.account_labels.canonical_account_label`:
   нижний регистр, `-` → `_`). Допустимо: латиница, цифры, `_`, `-`, до 32 символов.
   Метка `default` зарезервирована за безымянным ключом `TELEGRAM_SESSION_STRING`.
   Ключи с недопустимой меткой (например, вписанные руками) сервер и CLI игнорируют с
   предупреждением: метка попадает в текст команды перелогина и должна быть безопасной.
2. **Один аккаунт** — для пользователя как сейчас: безымянный ключ допустим, метку не
   спрашиваем, `account` не нужен, режим входа в чате по QR, если сессии нет. Отличие
   только внутри: аккаунт тоже подключается лениво (решение 6). Отозванная единственная
   сессия обнаруживается на первом вызове, а не при старте: сервер удаляет её (как сейчас
   `_relogin_user_message`) и просит перезапустить клиент — после перезапуска будет QR в
   чате.
3. **Второй аккаунт** — установщик спрашивает метку для нового (обязательно) и предлагает
   назвать первый (Enter — оставить `default`). Переименование первого — перенос значения
   в ключ с меткой одной записью файла. Других переименований нет (решение 10).
4. **Аккаунт по умолчанию** — `TELEGRAM_DEFAULT_ACCOUNT=<метка>` в `config.env`. Установщик
   спрашивает его при добавлении второго аккаунта; можно ответить «никакого» — тогда
   всегда спрашивать.
5. **Выбор аккаунта.** Если `account` не указан: аккаунт один → он; есть умолчание → оно;
   нет умолчания и аккаунтов несколько → ответ-вопрос текстом (с перечнем меток), а не
   ошибка и не опрос всех. **Ни один инструмент не опрашивает все аккаунты неявно.** Это
   касается и инструментов ожидания сообщений (`wait_for_new_message`,
   `wait_for_settled_message` — «дождись ответа Васи»): без `account` они ждут в аккаунте
   по умолчанию, а если его нет — модель спрашивает, в каком аккаунте ждать. «Во всех
   аккаунтах» — только по явной просьбе пользователя: модель вызывает инструмент по
   каждому аккаунту отдельно.
6. **Ленивое подключение — для любого числа аккаунтов.** При старте сервера не
   подключается никто: аккаунт подключается при первом обращении к нему, прогревается
   только он. Сервер стартует всегда — даже если все сессии мертвы. Сбой одного аккаунта
   (при подключении или посреди работы) не затрагивает другие и не роняет процесс.
   Побочный плюс: из нескольких копий сервера, которые запускают Claude Desktop и ChatGPT
   Work, к Telegram подключается только та, через которую идут запросы.
7. **Отпавший аккаунт** (сессия отозвана, дубликат, не удалось подключиться): понятное
   сообщение с меткой; для отзыва и дубликата — **команда перелогина именно этого
   аккаунта** (по ОС, как сейчас для `--relogin`) и просьба перезапустить клиент; для сети
   и таймаута — «повторите позже». В режиме нескольких аккаунтов сессию автоматически
   не удаляем; при одном — удаляем, как сейчас (решение 2).
8. **Вход и перелогин трогают только ключ своего аккаунта.** Сегодняшний `clear_session()`
   сносит все ключи — для нескольких аккаунтов это недопустимо. Установщик никогда не
   перезаписывает `config.env` целиком, если в нём есть сессии.
9. **Скилл `telegram-digest`:** аккаунтов несколько и неясно, какой, — всегда спрашивать;
   ясно — не спрашивать. «Всё непрочитанное» — по одному аккаунту, если пользователь не
   сказал «во всех».
10. **Не делаем:** вход второго аккаунта по QR в чате (только установщик); копию
    `runner._main` к себе; пул `TELEGRAM_SESSION_STRINGS` (это несколько сессий **одного**
    аккаунта — другая задача); переименование аккаунтов после заведения (кроме `default` →
    метка при добавлении второго, решение 3); перечитывание `config.env` без перезапуска
    клиента.
11. **Лента входящих** (`enable_incoming_feed`; только Claude Code, только при явном
    включении, в режиме read-only скрыта): фоновая запись каждого входящего сообщения в
    файл, за которым следит Claude Code и будит агента. Лента получает события только от
    подключённых аккаунтов, а параметра `account` у неё нет. Поэтому её включение
    подключает все аккаунты — иначе она молча ничего не пишет. Это не неявный опрос:
    пользователь сам включает ленту ради всех входящих.

Инварианты проекта действуют целиком (особенно 1, 2, 3, 5, 6, 7, 8, 9 из `CLAUDE.md`):
read-only по умолчанию, секреты только в `config.env`, session-строка не печатается,
пустая строка в окружении — «не задано» (относится и к `TELEGRAM_DEFAULT_ACCOUNT`).
Инварианты 5 и 8 обновляются в фазе 06.

## Что выяснено про апстрим

Закреплён по SHA в `pyproject.toml` (`208d067…`); номера строк ниже не фиксируем — искать
по именам. Сверено по исходникам этого SHA, Telethon 1.45.0 и `mcp` 1.30.0.

- `telegram_mcp/runtime.py`: `_discover_accounts()` при импорте строит клиентов из ключей
  `TELEGRAM_SESSION_STRING_<LABEL>` / `TELEGRAM_SESSION_NAME_<LABEL>` (метку только
  канонизирует, не проверяет); безымянный ключ — метка `default`; пул и
  `TELEGRAM_SESSION_NAME` рядом с метками дают `OPTIONAL_ACCOUNTS`. `clients` — словарь
  метка → клиент. `get_client(account)` без аккаунта при нескольких клиентах бросает
  `ValueError`; с неизвестной меткой — тоже `ValueError`.
- **Источник истины о числе аккаунтов в сервере — `runtime.clients`** (`is_multi_mode()`),
  а не разбор окружения: состав клиентов у апстрима учитывает пул, `_NAME`-ключи и
  выброшенные нами битые строки. Считать в момент вызова: в режиме входа клиенты
  подменяются после импорта.
- `runtime.with_account(readonly)`: аккаунт указан → используется он; не указан и
  несколько аккаунтов: чтение — опрос всех, изменяющий — строка-ошибка. Модули
  `telegram_mcp/tools/*` получают `with_account` через `from telegram_mcp.runtime import *`
  в момент импорта (`runtime.__all__` — все имена модуля, кроме `__…`). `runner.py`
  импортирует инструменты в начале файла, поэтому подмена декоратора возможна только
  **до** `from telegram_mcp import runner` (в `server.py` это место между настройкой
  окружения и импортом `runner`; `rich_buttons` и наши инструменты транскрипции
  импортируют `with_account` позже и тоже получат подменённый).
- **Не всё идёт через `with_account`.** В `tools/events.py` у `wait_for_events`,
  `wait_for_new_message`, `wait_for_settled_message` есть параметр `account`, но нет
  декоратора: без `account` они ждут события всех аккаунтов (неявный опрос всех), а
  `_wait_target` подключает клиента через `resolve_entity` → `ensure_connected` без замка
  сессии. `wait_for_events` у нас скрыт; два других видны в read-only (есть в
  `tests/test_upstream_surface.py`). `register_incoming_handlers()` при импорте вешает
  обработчики на всех клиентов — неподключённый клиент событий не даёт.
  `enable_incoming_feed` (лента входящих) параметра `account` не имеет и никого не
  подключает; в read-only скрыт апстримом (нет `readOnlyHint`), в режиме `all` виден.
  `list_accounts` без декоратора вызывает `get_me()` по всем клиентам.
- Все инструменты под `with_account` возвращают `str` (или без аннотации) — ответ-вопрос
  строкой вместо результата допустим, схема вывода не ломается.
- `runner._main()` подключает **все** клиенты параллельно через `_connect_or_skip` →
  `_connect_authorized_client`. `_main` ищет `_connect_or_skip` в глобалах модуля в
  момент вызова — подмена атрибута `runner._connect_or_skip` работает. Любое исключение
  при старте завершает сервер (`sys.exit(1)`).
- `_connect_authorized_client(label, client)`: берёт `SessionLock` (ожидание до
  `TELEGRAM_LOCK_GRACE_SECONDS`, по умолчанию 20 с; блокирующе, через `to_thread`) и
  **сразу** кладёт его в `runner._session_locks[label]`, затем `connect()` с повторами при
  `AuthKeyDuplicatedError` (паузы 2+4+8 с, 4 попытки), затем `is_user_authorized()` и
  `_verify_expected_username`. **При неудаче замок остаётся занятым** — освобождает его
  только `_connect_or_skip` (для опциональных) или `finally` в `_main`. Повторная попытка
  без освобождения перезапишет запись в словаре (утечка дескриптора), а при
  `TELEGRAM_SESSION_LOCK=exclusive` упрётся в собственный замок и через 20 с бросит
  `SessionLockError`.
- **Отозванная сессия при подключении — это `runner._NotAuthorized`**, а не
  `AuthKeyUnregisteredError`: Telethon в `is_user_authorized()` глотает `RPCError` и
  возвращает `False`. Чужой аккаунт в сессии — `RuntimeError` из
  `_verify_expected_username`. Посреди работы отзыв приходит из инструмента как
  `AuthKeyUnregisteredError` / `SessionRevokedError` / … (`_RELOGIN_SESSION_ERRORS`).
- После подключения `_main` фоном вызывает `get_dialogs()` (без лимита — все диалоги) по
  каждому клиенту. Прогрев — замыкание внутри `_main`, подменить нельзя: для
  неподключённого клиента он печатает в stderr
  `Entity cache warm failed for '<метка>': Cannot send requests while disconnected` —
  безвредно, принимаем, `_main` не копируем.
- `finally` в `_main` отключает все клиенты (`return_exceptions=True`; для никогда не
  подключавшегося клиента `disconnect()` безопасен) и освобождает все замки из
  `_session_locks`.
- Прогрев нужен не всегда: `resolve_entity` сам вызывает `get_dialogs()` при промахе кэша.
  `get_chats`, `list_chats`, `get_direct_chat_by_contact`, `get_contact_chats`,
  `export_unread_messages` вызывают `get_dialogs()` как источник данных — это не промах.
- 58 из 147 инструментов вызывают `ensure_connected` сами, ещё часть — через
  `resolve_entity`. `ensure_connected` подключает неподключённый клиент **без** замка
  сессии и кэширует неудачу на 30 с — поэтому подключение делаем в декораторе раньше,
  через `_connect_authorized_client`.
- **Общий таймаут вызова — 55 с** (`TELEGRAM_TOOL_TIMEOUT_SECONDS`, `_install_annotation_hook`
  оборачивает весь вызов в `wait_for`). Подключение (замок до 20 с + повторы ~14 с +
  собственные повторы `connect` в Telethon) может в него не уложиться: отмена прилетит
  посреди подключения.
- Telethon привязывает клиента к циклу событий при первом `connect()` — ленивое
  подключение в цикле `asyncio.run(_main())` безопасно.
- `mcp.server.fastmcp` (SDK 1.30.0): `Tool.fn` — обычное поле, схема считается при
  регистрации; наш код уже достаёт инструменты из `mcp._tool_manager._tools`. Подмена
  `Tool.fn` позволяет обернуть уже зарегистрированный инструмент.

В нашем коде: `config.py` (`clear_session` сносит все ключи, `_has_session`, `write_values`
переписывает файл на месте — так сохраняется ACL на Windows; `_drop_unreadable_session_strings`),
`server.py` (`_saved_session_is_dead` при старте ходит в сеть, проверяет только безымянный
ключ и при отзыве вызывает `clear_session()` по всем — он нужен был лишь потому, что
апстрим падает на мёртвой сессии до первого инструмента; `_relogin_user_message` тоже
чистит все ключи; `_install_login_client`, `_activate_reading_tools` — после входа по QR
клиент уже подключён и авторизован; `_HIDDEN_UPSTREAM_TOOLS`), `login.py`
(`_persist_session` пишет безымянный ключ), `terminal_login.py` (`clear_session` +
безымянный ключ; коды выхода 0/1/2 argparse/3), `relogin.py` (команды `--relogin` без
метки).

Установщики: скачиваются из `main`, а пакет ставят из **последнего релизного тега**
(`_resolve_repo_ref` / `Resolve-RepoRef`). При коде 3 от входа («Telegram отклонил
api_id/api_hash») они вызывают `write_config_env` / `Write-ConfigEnv`, которые **пишут
`config.env` с нуля** (четыре строки, старый файл — в `.bak-…`). Самопроверка
(`self_check` / `Invoke-SelfCheck`) зовёт `check_transcription_access()` без `account`.
CI `install` останавливается до входа в Telegram.

## Фаза 01. Ключи аккаунтов в `config.py` и вход в терминале по метке

**Цель.** Один набор функций знает, как называются ключи сессий, и умеет читать, писать,
переименовывать и чистить их по метке; командой `telegram-mcp-ag-login` можно войти в
конкретный аккаунт, не задевая остальные, а установщики получают метки без разбора
`config.env` своими силами.

**Входит — `config.py`**

- [ ] `normalize_label()` (каноническая форма как у апстрима) и проверка допустимости метки с
      понятным русским сообщением (латиница — пример: «рабочий» → `work`); `default`

## Фаза 02. Выбор аккаунта: по умолчанию или вопрос

**Цель.** Любой инструмент без явного `account` берёт единственный аккаунт или аккаунт по
умолчанию, а если умолчания нет и аккаунтов несколько — возвращает вопрос; опроса всех
аккаунтов не бывает.

**Опирается на:** фаза 01 — `default_account`, нормализация меток.

**Входит**

- [ ] Свой `with_account(readonly=False)` в нашем пакете; в `server.py` импортировать

## Фаза 03. Ленивое подключение всех аккаунтов

## Фаза 04. Отпавший аккаунт: сообщения, перелогин, `list_accounts`

**Цель.** Когда аккаунт недоступен — при подключении или посреди работы, — пользователь

**Опирается на:** фаза 03 — состояние «недоступен» и причина; фаза 02 — `ContextVar`;
фаза 01 — `relogin.instructions(account=...)`, `clear_session(label=...)`.

**Входит**

- [ ] Классы причин: сессия отозвана / не авторизована (`runner._NotAuthorized`,

      `_verify_expected_username`), прочее (сеть, таймаут, `SessionLockError`). Для первых

      сервер покажет QR в чате; альтернатива — команда в терминале». Это заменяет

      вызывается**, ключи не удаляются.
- [ ] Свой `list_accounts` вместо апстримного (убрать апстримный из реестра так же, как

      аккаунт, режим нескольких аккаунтов не удаляет ключи, режим одного — удаляет и
      предлагает QR, `list_accounts` не обращается к сети; `tests/test_upstream_surface.py`

**Не входит:** вход второго аккаунта в чате; хранение отображаемых имён аккаунтов.

**Ловушки**
