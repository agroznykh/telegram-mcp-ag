# Технические детали

Этот документ — для тех, кому интересно, как устроен telegram-mcp-ag внутри.
Для установки и обычного использования он не нужен — см. [README.md](README.md).

## Что это такое

Тонкая обёртка над апстрим-проектом
[`chigwell/telegram-mcp`](https://github.com/chigwell/telegram-mcp): он даёт
чтение чатов через MTProto (нативный протокол Telegram), а этот проект
добавляет расшифровку голосовых, видео-кружков и аудио — тоже через нативный
API Telegram, без сторонних сервисов распознавания речи.

Апстрим закреплён на конкретном коммите (SHA указан в `pyproject.toml`), а не
на плавающей версии: `telegram_mcp.runtime` из апстрима — единственная точка
интеграции, и она не даёт гарантий совместимости между коммитами. Обновление
пина — осознанный шаг с проверкой, что изменилось, а не рутинное обновление
зависимости.

Оба проекта — этот и апстрим — распространяются под лицензией **Apache-2.0**.

## Стек

```
Python 3.14 / Telethon (MTProto) / MCP SDK / setuptools
```

### Почему установщик ставит свой Python

Сначала брали любой подходящий Python с машины, теперь ставим свой 3.14 через `uv`:

- свой Python стабильнее: версия одна и проверенная;
- если окружение собрано на Python из Homebrew, Homebrew может его удалить, и сервер сломается;
- лишнее место не проблема: на любой машине обычно и так установлено много Python.

## Read-only режим и скачивание медиа

По умолчанию сервер поднимается с `TELEGRAM_EXPOSED_TOOLS=read-only` — из всех
MCP-инструментов регистрируются только помеченные `readOnlyHint=True`.
Отправка сообщений и любые изменяющие действия физически недоступны в
конфигурации по умолчанию, а не просто «не упомянуты в подсказках».

Скачивание файлов включается вручную значением `read-only+download_media`: к
набору добавляется ровно один инструмент, апстримный `download_media`. Он пишет
файл на диск пользователя и ничего не меняет в Telegram. Установщики значение
не меняют и существующий `config.env` не переписывают.

### Куда скачиваются файлы

`download_media` пишет только внутрь «разрешённых папок». Источники:

1. Папки клиента (MCP Roots): Claude Code сообщает папку проекта, файл ложится
   в `<проект>/<TELEGRAM_DOWNLOAD_SUBDIR>/`.
2. `TELEGRAM_ALLOWED_ROOTS` — запасной вариант, если клиент папок не сообщил:
   не поддерживает Roots, прислал пустой список или не ответил за 10 секунд
   (два последних случая — только при `TELEGRAM_ALLOW_SERVER_ROOTS_FALLBACK=1`).

Ключи, которые `config.py` дописывает в `config.env` при запуске, если
`download_media` включён (`all` или `read-only+download_media`, без исключения
`-download_media`) и ключей там нет. Без скачивания ничего не дописывается и
папка не создаётся: `download_media_enabled()` повторяет разбор режима апстрима,
тест сверяет их. Уже записанное значение `config.py` не перезаписывает. Пустое
значение сервер всё равно считает «не задано» (инвариант 7) и берёт умолчание,
так что пустым ключом запасную папку отключить нельзя — только выключить
`download_media`:

| Ключ | Значение по умолчанию | Смысл |
|---|---|---|
| `TELEGRAM_ALLOWED_ROOTS` | `<Загрузки>/Telegram` | запасная папка |
| `TELEGRAM_ALLOW_SERVER_ROOTS_FALLBACK` | `1` | запасная папка и при пустом списке или молчании клиента |
| `TELEGRAM_DOWNLOAD_SUBDIR` | `Telegram` | подпапка в проекте; в запасной папке файлы лежат без лишней вложенности |

`<Загрузки>` определяет `default_download_root()`: на macOS `~/Downloads`; на
Windows известная папка Downloads (`SHGetKnownFolderPath`), потому что её могли
перенести на другой диск; на Linux `XDG_DOWNLOAD_DIR` из
`~/.config/user-dirs.dirs`. При любой неудаче — `~/Downloads`. Если `config.env`
записать не удалось, `server.py` подставляет те же значения в окружение.

### Защита от недоступной папки

Апстрим при старте создаёт каждую папку из `TELEGRAM_ALLOWED_ROOTS` и завершает
процесс, если не смог. На macOS «Загрузки» защищены системой: если пользователь
отказал клиенту в доступе, сервер не запустился бы вообще.
`_drop_unusable_allowed_roots()` (первая строка `main()`) пробует создать
каждую папку и проверяет запись; недоступные выбрасывает с сообщением в stderr.
Скачивание тогда работает только в папке проекта.

## MCP-инструменты

- `check_transcription_access` — статус Premium, остаток бесплатной недельной
  квоты на расшифровку, дата её обновления.
- `transcribe_voice_messages` — расшифровка списка сообщений (даже если он из
  одного элемента); сам разбивает список на части с учётом лимита времени
  одного вызова MCP. Одиночного варианта инструмента намеренно нет — это
  убирает саму возможность вызывать расшифровку по одному сообщению в цикле.
- `telegram_login_start` / `telegram_login_check` — вход по QR-коду прямо в
  чате, для случаев, когда сессии ещё нет.
- Плюс весь набор инструментов чтения из апстрима (чаты, папки, контакты,
  история сообщений) — в режиме `read-only`.

## Как хранятся секреты

Все секреты (`api_id`, `api_hash`, строка Telegram-сессии) живут в одном
файле — `~/telegram-mcp-ag/config.env`, который создаётся с правами `600`
(чтение и запись только владельцу; на Windows аналогичное ограничение
обеспечивает ACL файловой системы). В конфигах MCP-клиентов
(`.mcp.json`, `~/.codex/config.toml`, `claude_desktop_config.json`) остаётся
только путь к исполняемому файлу — сами секреты туда никогда не попадают,
потому что такие файлы гораздо чаще случайно коммитят в git или показывают
на скриншоте.

Строка сессии Telegram равносильна полному доступу к аккаунту. Подробный
разбор угроз и что делать при подозрении на утечку — в [SECURITY.md](SECURITY.md).

### Вход по QR в чате

Через переписку с ассистентом проходит только одноразовый login-токен
ссылкой `tg://login` — не номер телефона, не код, не пароль двухфакторной
аутентификации и не строка сессии. Сам QR-код открывается в браузере
локальной страницей, которая сама перечитывается; сервер подменяет на ней
истёкший код свежим (код живёт около 30 секунд). Картинки QR в чате нет:
устаревший код там — только неудачное сканирование. Если у аккаунта включён облачный пароль (2FA), его
запрашивает системное окно ОС (`zenity`/`kdialog` на Linux, `osascript` на
macOS, защищённый ввод PowerShell на Windows) — используется один раз и не
сохраняется никуда: ни в чат, ни в файл, ни в системное хранилище паролей.

## Почему не поддерживаются ChatGPT web и мобильное приложение

Этот сервер — локальный процесс, который общается с клиентом по протоколу
stdio (стандартный ввод/вывод), а не по сети. ChatGPT web и мобильное
приложение умеют подключать только **удалённые** MCP-серверы по HTTPS —
то есть потребовался бы отдельный сервер, доступный из интернета, которому
нужно было бы доверить сессию Telegram. Вместо этого сессия хранится только
локально, на компьютере пользователя, поэтому эти два клиента в принципе не
могут быть поддержаны без изменения всей модели угроз проекта.

## Сколько экземпляров запускают десктопные клиенты

Проверено вручную на macOS (по `ps`, родительским процессам и вызову
`check_transcription_access` в каждом режиме), октябрь 2026, на версиях Claude
for Mac 3.6556.2 (20c019) и ChatGPT 26.1016.62342 (Codex & OWL).
Официальной документации с такими деталями у производителей нет — это
наблюдения; при смене версии приложения картина может измениться, тогда
повторите проверку.

- **Claude Desktop.** Два экземпляра стартуют вместе с приложением (родитель —
  главный процесс приложения), ещё до открытия какой-либо сессии. Инструмент
  доступен в Chat. Сессии Cowork и Code ведёт встроенный Claude Code: он
  запускает собственный, третий экземпляр.
- **ChatGPT Desktop.** До открытия режима Work экземпляров нет. Режим Chat
  инструментов не получает. При первой сессии Work встроенный `codex app-server`
  запускает два экземпляра с разницей около секунды; при закрытии сессии один из
  них завершается, второй остаётся. Настройка берётся из общего
  `~/.codex/config.toml`.

Поэтому замок сессии по умолчанию `shared`: все экземпляры работают с одной
машины, то есть с одного IP (см. «Одна сессия — одна машина»). С замком
`exclusive` лишние экземпляры отказываются стартовать.

## Одна сессия — одна машина

`api_id`/`api_hash` можно свободно переиспользовать между машинами — это не
секрет уровня сессии, они привязаны к Telegram-приложению, а не к конкретному
входу. А вот `TELEGRAM_SESSION_STRING` — нет: если Telegram видит одну и ту же
строку сессии с разных IP, он отвечает `AUTH_KEY_DUPLICATED` и убивает обе
сессии.

### Как работает `--relogin`

Без флагов установщик сам решает, нужен ли вход: если `~/telegram-mcp-ag/config.env`
уже содержит `api_id`/`api_hash`/строку сессии, он их переиспользует и вход
пропускает (`has_full_config` в `install.sh`). `--relogin`/`-Relogin` эту
проверку отключает и форсирует вход заново, даже если конфиг уже есть на
диске; пакет переустанавливается вместе с логином, как при обычной установке.

`api_id`/`api_hash` при входе не спрашиваются, если они уже есть в
`config.env` (`load_api_credentials` в `install.sh`, `Read-ConfigCredentials`
в `install.ps1`): они принадлежат приложению на my.telegram.org, а не сессии,
и после отзыва сессии остаются действительными. Спрашиваются они, только когда
их в файле нет или Telegram их не принял — команда входа
`telegram-mcp-ag-login` выходит тогда с кодом 3, установщик спрашивает ключи
заново и повторяет вход. Новый вход заменяет все прежние сессии в `config.env`,
остальные настройки файла сохраняются.

Отсюда две разные ситуации, которые легко перепутать:

- **Вторая машина** формально в этом флаге не нуждается: раз на ней ещё нет
  `config.env`, обычная установка без флагов и так пройдёт вход — `has_full_config`
  вернёт «нет», сработает та же ветка, что и с `--relogin`. Поэтому README
  рекомендует для второй машины обычную команду установки, а не `--relogin`.
- **Сессия умерла на этой же машине** — вручную отозвана в Telegram
  (Settings → Devices, без предварительного `--uninstall`) или убита
  `AUTH_KEY_DUPLICATED` (см. выше). Если сервер успел увидеть отзыв, он сам
  удаляет мёртвую сессию из `config.env` (`clear_session` в `config.py`) —
  тогда следующий запуск сервера предложит вход в чате, а обычный запуск
  установщика проведёт вход и без флага. Но пока сервер отзыв не заметил,
  `config.env` выглядит полным, и обычный запуск установщика вход пропустил бы —
  здесь `--relogin`/`-Relogin` необходим по-настоящему, и именно этот сценарий
  README описывает в разделе «Если ассистент перестал видеть Telegram».

## Структура репозитория

```
src/telegram_mcp_ag/
├── server.py     # MCP-инструменты транскрипции поверх апстрима, выбор режима
├── login.py      # вход по QR прямо в чате, когда сессии ещё нет
├── terminal_login.py  # вход в терминале для установщиков: QR, запасной — по телефону
├── relogin.py    # команда перелогина под ОС машины — для сообщений обоих режимов
├── config.py     # креды из окружения и ~/telegram-mcp-ag/config.env
└── __init__.py
tests/            # pytest, без сети
examples/         # образцы конфигов клиентов (только плейсхолдеры)
install.sh        # установщик для macOS/Linux
install.ps1       # установщик для Windows
```
